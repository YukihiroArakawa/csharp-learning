ページングされたtask一覧を読む

今回の課題

  • 目安時間：35〜45分
  • 前提：Minimal APIのquery parameter bindingとHTTP status codeを説明できる
  • 目的：page number方式のAPI契約、入力検証、切り出し計算、metadataの役割をコードから説明できる

最終課題の最初の縦切りとして、CodexがGET /tasksへページングを実装しました。現在は固定dataを使い、HTTP契約と ページング計算を先に確定しています。次の課題でdata sourceをEF Coreへ置き換えても、clientから見えるquery parameterとresponseの形は 変えません。学習者は実装と統合テストを読み、どの入力からどの範囲が返るかを説明します。

ページングが解決する問題

一覧endpointが全件を返すと、data増加に比例してdatabaseの読み取り量、application memory、JSON size、network転送量が増えます。 clientが画面に20件しか表示しない場合でも、残りを取得する費用が発生します。ページングは一度に返す件数を制限し、clientが必要な範囲を 明示して取得できるようにします。

今回は1から始まるpageと、1ページの件数を表すpageSizeを採用します。指定がなければpage 1、20件です。 pageSizeの上限を100にすることで、clientが極端に大きな値を指定して実質的な全件取得に戻すことを防ぎます。

request意味返るID
?page=1&pageSize=2先頭から2件1, 2
?page=2&pageSize=2先頭2件を飛ばして次の2件3, 4
?page=4&pageSize=2存在する5件より後空のitems

itemsだけでなくmetadataも返す

responseはtask配列だけではなく、items、page、pageSize、totalCountを返します。 clientはtotalCountとpageSizeから全ページ数を計算でき、現在のpage表示や「次へ」buttonの有効・無効を判断できます。 requestされたpageが最終pageより後でも、request形式自体は正しいため404にはせず、metadataを保った空のitemsを200で返します。 

{
  "items": [

    { "id": 4, "title": "READMEを更新する", "isCompleted": false }
  ],

今回読むC#の形

default parameter

IResult (int page = 1, int pageSize = 20) =>

= 1と= 20はargumentが省略された場合のdefault valueです。ASP.NET Coreはquery stringに値があればintへ変換し、 なければdefaultを使います。Javaのmethod parameterには同じdefault argument構文がないため、Springではrequest parameter annotationの default設定やmethod内の補完で表すことが一般的です。

list pattern風のcollection expression

errors[nameof(page)] = ["pageは1以上を指定してください。"];

右辺の角括弧は、要素を一つ持つstring[]を作るcollection expressionです。左辺の期待typeがstring[]なのでcompilerが 配列typeを決定します。nameof(page)は文字列"page"をcompile時に得るため、parameter名をrenameした際も追従します。

generic record

public sealed record PagedResponse<T>(
    IReadOnlyList<T> Items,
    int Page,
    int PageSize,
    int TotalCount);

Tに一覧要素のtypeを渡すことで、同じページング契約をtask以外にも再利用できます。今回は PagedResponse<TaskSummary>となり、Itemsはtaskの読み取り専用listです。

実装コードを実行順に読む

05-capstone/TaskManagementApi/Program.cs

app.MapGet("/tasks", IResult (int page = 1, int pageSize = 20) =>
{
    var errors = new Dictionary<string, string[]>();

    if (page < 1)
    {
        errors[nameof(page)] = ["pageは1以上を指定してください。"];
    }

    if (pageSize is < 1 or > 100)
    {
        errors[nameof(pageSize)] = ["pageSizeは1以上100以下を指定してください。"];
    }

    if (errors.Count > 0)
    {
        return Results.ValidationProblem(errors);
    }

request時にframeworkがquery parameterをbindingした後、application固有の範囲を検証します。複数項目が不正でも一度に返せるよう dictionaryへerrorを蓄積し、1件以上なら400 Problem Detailsを返してページ計算へ進みません。 

var items = tasks
    .OrderBy(task => task.Id)
    .Skip((page - 1) * pageSize)
    .Take(pageSize)
    .ToList();

先にID順を確定します。順序がなければ同じpage requestで同じ要素が返る保証を作れません。 (page - 1) * pageSize件を飛ばし、そこから最大pageSize件を取得します。page 2、pageSize 2なら (2 - 1) * 2 = 2件を飛ばすため、ID 3から始まります。 

return Results.Ok(new PagedResponse<TaskSummary>(
    items,
    page,
    pageSize,
    tasks.Count));

切り出した要素とrequest条件に加え、切り出す前の全件数を返します。TotalCountをitems.Countにすると、常に現在pageの 件数しか伝わらず、clientが全体のページ数を計算できません。

統合テストが固定する契約

TaskPaginationTestsはproductionのProgramをtest hostとして起動し、HTTP requestを送ります。page 2ではID 3、4と metadataを検証し、page 0では400、存在する範囲より後のpageでは200と空listを検証します。これにより次回data sourceをEF Coreへ 変更したときも、外部契約が変わっていないことを検出できます。 

var response = await client.GetAsync("/tasks?page=2&pageSize=2");

response.EnsureSuccessStatusCode();
var page = await response.Content
    .ReadFromJsonAsync<PagedResponse<TaskSummary>>();

Assert.Equal(5, page.TotalCount);
Assert.Equal([3, 4], page.Items.Select(task => task.Id));
