LINQがSQLへ翻訳される境界を読む

今回の課題

  • 目安時間：35〜45分
  • 前提：LINQの遅延実行、IEnumerable<T>とIQueryable<T>の違いを説明できる
  • 目的：EF Coreがqueryを組み立てる段階と、SQLへ翻訳してdatabaseへ送る段階をコードから特定する

CodexがSQLiteからtask一覧を取得するGET /tasksを実装しました。query parameterがある場合だけ絞り込み、 category名を含むresponseへprojectionします。学習者はLINQ methodと実際のSQLを対応付け、どの行でdatabase I/Oが 始まるかを読みます。

IQueryableは結果ではなくqueryの設計図

dbContext.Tasksから始まるLINQは、通常のList<TaskItem>をmemory上で絞り込む処理ではありません。 EF Core providerが理解できるexpression treeとして「どのtableから、どの条件で、どの順序・形のdataを取るか」を蓄積します。 WhereやSelectを呼んだ段階では、まだSQLをdatabaseへ送っていません。

最後にToListAsyncなどのterminal operationを呼ぶと、EF Coreは完成したexpression treeをdatabase providerへ渡します。 SQLite providerがSQLへ翻訳し、parameterとともにdatabaseへ送信します。返されたrowをTaskSummaryへmaterializeして、 List<TaskSummary>としてapplicationへ戻します。

実装を実行順に読む

app.MapGet("/tasks", async (
    bool? completed,
    TaskDbContext dbContext,
    CancellationToken cancellationToken) =>
{

Minimal APIがcompletedをquery parameter、TaskDbContextをrequest scopeのDI、 CancellationTokenをrequest中断通知からbindingします。client切断やrequest timeoutでキャンセルされれば、 下流のdatabase I/Oにも停止要求を伝えられます。 

IQueryable<TaskItem> query = dbContext.Tasks.AsNoTracking();

ここではTasks tableをqueryする起点を作っただけで、database accessはまだ発生しません。 AsNoTrackingは取得entityを更新予定がないことをEF Coreへ伝え、change trackerへ登録する処理を省きます。 読み取り専用endpointに適した指定です。 

if (completed is not null)
{
    query = query.Where(
        task => task.IsCompleted == completed.Value);
}

query parameterが指定された場合だけexpression treeへfilterを追加します。lambdaは通常のC# delegateとして各rowに対して 実行されるのではなく、EF Coreが解析してSQLのWHEREへ変換します。値はSQL文字列へ直接連結されず、 @completed_Value parameterとして送られます。 

var tasks = await query
    .OrderBy(task => task.Id)
    .Select(task => new TaskSummary(
        task.Id,
        task.Title,
        task.IsCompleted,
        task.Category == null ? null : task.Category.Name))
    .ToListAsync(cancellationToken);

OrderByは結果順を安定させます。Selectはentity全体ではなくresponseに必要な4項目だけを選びます。 optional relationのCategoryを参照するため、EF Coreはcategoryなしのtaskも残るLEFT JOINを生成します。

ToListAsyncが実行境界です。この行で初めてquery全体がSQLへ翻訳・送信され、結果を非同期に読み取ります。 await後のtasksはIQueryableではなく、取得済みのmemory上のlistです。

実際に生成されたSQL

SELECT "t"."Id", "t"."Title", "t"."IsCompleted", "c"."Name"
FROM "Tasks" AS "t"
LEFT JOIN "Categories" AS "c" ON "t"."CategoryId" = "c"."Id"
WHERE "t"."IsCompleted" = @completed_Value
ORDER BY "t"."Id"

IQueryableを層の外へ漏らさない理由

IQueryableは未実行queryなので、呼び出し側がさらに条件を追加したり、複数回列挙して複数回SQLを実行したりできます。 どのSQLがいつ実行されるか、DbContextがまだ有効か、どこまでがdatabase側評価かが曖昧になります。

database accessを担当する層でfilter・projection・materializationを完了し、上位層へはList<TaskSummary>など 取得済み結果を返すと、I/O boundaryとquery責任が明確になります。すべてのarchitectureで絶対禁止という意味ではありませんが、 意図せずqueryを変更・再実行できるAPIを公開しないことが安全なdefaultです。

JPA / Hibernateとの比較

Spring Data JPAのrepository methodやCriteria API、JPQLを実行時にSQLへ変換する流れに近いです。 LINQではC#のlambdaとmethod chainがexpression treeになり、providerが解析します。 Java Streamのfilterを既に取得済みcollectionへ適用する場合とは異なり、ここではfilterがdatabaseへ押し込まれます。

コードリーディング課題

  1. Whereを呼んだ時点とToListAsyncを呼んだ時点では、database accessの有無がどう違いますか。
  2. 生成SQLのWHERE、LEFT JOIN、ORDER BYは、それぞれどのLINQ記述から生まれましたか。
  3. この読み取り専用endpointでAsNoTrackingを使う理由と、ToListAsyncへCancellationTokenを渡す理由を説明してください。

query構築とI/O実行の境界を示し、LINQとSQLを対応付けられれば完了です。
