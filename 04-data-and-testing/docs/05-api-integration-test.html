WebApplicationFactoryでAPI統合テストを読む

今回の課題

  • 目安時間：35〜45分
  • 前提：サービスを直接呼ぶテストと、SQLiteインメモリdatabaseの生存期間を説明できる
  • 目的：WebApplicationFactoryがapplicationを起動する範囲と、API統合テストが保証する範囲を説明できる

CodexがGET /tasks?completed=falseへrequestを送り、status codeとJSON responseを検証する統合テストを実装しました。 学習者はコードを手入力せず、前回のサービステストとの違い、production用DI登録をtest用へ差し替える箇所、requestがresponseになるまでの 経路を読みます。

API統合テストが確認するもの

前回のテストはTaskQueryServiceをnewして直接呼びました。そのため、queryのfilter・order・projectionは確認できても、 URLが正しく登録されているか、completed=falseがC#のbool?へ変換されるか、serviceがDIから解決できるか、結果が JSONへ変換されるかは確認していません。

今回のテストはWebApplicationFactory<Program>でproduction applicationのentry pointを指定します。factoryは Program.csの起動処理を使ってtest用hostを組み立て、ASP.NET Core pipelineへ送れるHttpClientを作ります。 requestはrouting、query parameterのmodel binding、DI、endpoint、service、EF Core、SQLiteを通り、responseはJSON serializationを 通ってclientへ戻ります。

test serverはprocess外のweb serverを立てず、通常は実際のTCP portも開きません。そのため高速で安定しています。一方で、OSのnetwork、 reverse proxy、TLSなどは対象外です。「HTTP形式でapplication全体を結合して確認する」が、production環境を端から端まで再現する end-to-end testではない、という位置付けです。

WebApplicationFactoryとDIの差し替え

productionではappsettings.jsonのData Source=tasks.dbを使います。統合テストがこのfileを共有すると、local dataを 壊したり、以前の実行結果によってtestが変わったりします。そこで、productionの起動処理は再利用しつつ、 TaskDbContextの設定だけをtest専用のSQLiteインメモリdatabaseへ差し替えます。

ConfigureWebHostはtest hostを組み立てる準備段階で呼ばれます。既存のDbContextOptions<TaskDbContext>登録を RemoveAllで除き、同じservice typeをtest用connectionで再登録します。runtimeにrequestが来ると、DI containerは差し替え後の 登録を使ってrequest scopeごとのTaskDbContextを生成します。

factoryが一つのconnectionを開いたまま保持するのは、前回と同じくSQLiteインメモリdatabaseの寿命がconnectionの寿命だからです。 request scopeが終わってTaskDbContextが破棄されてもdatabaseは残り、factoryが破棄されるとconnectionとdatabaseも消えます。

実装コード：test用application factory

04-data-and-testing/TaskApi.Tests/TaskApiFactory.cs

public sealed class TaskApiFactory : WebApplicationFactory<Program>
{
    private readonly SqliteConnection connection;

    public TaskApiFactory()
    {
        SQLitePCL.Batteries_V2.Init();
        connection = new SqliteConnection("Data Source=:memory:");
        connection.Open();
    }

    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.ConfigureServices(services =>
        {
            services.RemoveAll<DbContextOptions<TaskDbContext>>();
            services.AddDbContext<TaskDbContext>(options =>
                options.UseSqlite(connection));
        });
    }

    protected override void Dispose(bool disposing)
    {
        base.Dispose(disposing);

        if (disposing)
        {
            connection.Dispose();
        }
    }
}

constructorがtest databaseの所有者です。ConfigureWebHostではproduction registrationのうちDB設定だけを置換し、endpointや TaskQueryServiceなどはproductionと同じ登録を残します。最後にxUnitがfixtureを破棄するとfactoryのDisposeが呼ばれ、 base classがhostやclient関連を片付けた後、保持していたconnectionを閉じます。

実装コード：HTTP requestからJSONまで

04-data-and-testing/TaskApi.Tests/TaskApiIntegrationTests.cs

public sealed class TaskApiIntegrationTests(TaskApiFactory factory)
    : IClassFixture<TaskApiFactory>
{
    [Fact]
    public async Task GetTasks_WhenCompletedIsFalse_ReturnsIncompleteTasksAsJson()
    {
        await using (var scope = factory.Services.CreateAsyncScope())
        {
            var dbContext = scope.ServiceProvider.GetRequiredService<TaskDbContext>();
            await dbContext.Database.EnsureCreatedAsync();

            dbContext.Tasks.AddRange(
                new TaskItem { Id = 2, Title = "完了済み", IsCompleted = true },
                new TaskItem { Id = 1, Title = "統合テストを読む", IsCompleted = false });
            await dbContext.SaveChangesAsync();
        }

        using var client = factory.CreateClient();

        var response = await client.GetAsync("/tasks?completed=false");

        response.EnsureSuccessStatusCode();
        var tasks = await response.Content.ReadFromJsonAsync<List<TaskSummary>>();
        var task = Assert.Single(Assert.IsType<List<TaskSummary>>(tasks));
        Assert.Equal(1, task.Id);
        Assert.Equal("統合テストを読む", task.Title);
        Assert.False(task.IsCompleted);
    }
}

ArrangeではfactoryのDI containerからscopeを一つ作り、test hostと同じSQLiteへ2件保存します。完了済みと未完了を混ぜることで、 query parameterがmodel bindingされ、filterへ届いたことを判定できます。scopeを閉じてもfactory所有のconnectionは開いているためdataは残ります。

ActではCreateClientが返したHttpClientからURLへGETを送ります。ASP.NET Coreがfalseをnullable boolへ変換し、 scoped serviceを生成し、endpointを実行します。serviceが返したTaskSummaryはframeworkによってJSONへserializeされます。

Assertでは、まず2xx responseであることを確認し、response bodyをList<TaskSummary>へdeserializeします。結果がnullでなく、 ちょうど1件で、未完了taskの値を持つことを検証します。これによりstatus、JSONの形、filter結果を一つのtestで結び付けています。

Spring Bootとの対応

役割としては、Spring Bootでapplication contextを起動し、MockMvcやtest用clientからcontrollerへrequestを送る統合テストに近いものです。 Spring側でもproduction beanをtest configurationで差し替えるように、今回はASP.NET Coreのservice collectionに登録された DbContextOptionsをtest用へ差し替えます。

framework固有のannotationやAPI名は異なりますが、productionの組み立てをできるだけ再利用し、外部依存だけを制御可能なtest doubleへ 置き換える考え方は共通です。今回のSQLiteはSQLを本当に実行するため、mockではなく軽量な実装への置換です。
