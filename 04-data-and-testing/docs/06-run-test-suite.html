solution単位で全テストを実行する

今回の課題

  • 目安時間：20〜30分
  • 前提：サービステストとAPI統合テストが検証する範囲を説明できる
  • 目的：solutionを検証入口として、production buildと全testを一つのcommandで実行できることを確認する

Codexがproduction projectとtest projectを束ねるsolutionを追加しました。学習者はsolutionが実行単位ではなくprojectの集合を表すこと、 dotnet testが依存関係の復元、build、test discovery、test実行を順に行うことを、fileと実行結果から読みます。

なぜprojectではなくsolutionを指定するのか

前回まではdotnet test TaskApi.Tests/TaskApi.Tests.csprojを実行していました。このtest projectは ProjectReferenceでTaskApiを参照しているため、現在の構成ではproduction projectも自動的にbuildされます。 したがって、このcommand自体が誤りだったわけではありません。

ただし、projectを直接指定するcommandは「どのprojectがフェーズ全体の検証対象か」という構成をcommandを知る人に依存させます。 将来別のtest projectが増えたとき、そのprojectを指定し忘れても既存commandは成功します。solutionへproduction projectとtest projectを 明示しておけば、開発者やCIは同じsolutionを入口にして、登録されたproject全体を復元・build・testできます。

Javaで複数moduleを親のMaven projectやGradle buildへ登録し、rootからmvn testやgradle testを実行する考え方に近いです。 solution自身はC# codeをcompileするprojectではなく、関連projectをまとめるworkspace兼command targetです。

.slnxとは

.slnxはsolutionをXMLで表す形式です。従来の.slnより内容が小さく、人間がproject一覧を読みやすい形式です。 今回は二つの.csprojへの相対pathだけを記録しています。どちらのprojectを先にbuildすべきかは、test project内の ProjectReferenceを.NET SDKが読み取って決定します。

solutionへprojectを登録してもproduction codeやruntime behaviorは変わりません。変わるのは開発時とCIで使う検証対象のまとまりです。 applicationを実行する場合は引き続きweb projectを指定し、全testを検証する場合はsolutionを指定します。

dotnet testの実行順序

dotnet test TaskApi.slnxを実行すると、最初にsolution内のprojectとpackage依存を読み、必要なNuGet packageをrestoreします。 続いてproduction projectをbuildし、それを参照するtest projectをbuildします。compile errorがあればtest methodを一つも実行せず、 この段階でcommandは失敗します。

build後、test runnerがtest assemblyから[Fact]の付いたmethodを発見して実行します。今回はサービスを直接呼ぶtestと、 WebApplicationFactoryからHTTP requestを送るtestの2件です。最後に成功・失敗・skipの件数を集計し、すべて成功すれば processの終了code 0を返します。CIは表示文字列を人間のように読むのではなく、この終了codeによって次の処理へ進むかを判断できます。

testが1件でも失敗する、buildできない、またはpackage restoreに失敗すると終了codeは0以外になります。したがって「2件成功」という 表示だけでなく、command全体が正常終了したことが自動化にとって重要です。fishでは直後の$statusで終了codeを確認できます。

実装コード

04-data-and-testing/TaskApi.slnx

<Solution>
  <Project Path="TaskApi.Tests/TaskApi.Tests.csproj" />
  <Project Path="TaskApi/TaskApi.csproj" />
</Solution>

root elementが一つのsolutionを表し、各Project elementがsolution fileからの相対pathでprojectを登録します。 test projectとproduction projectの両方が明示されているため、solutionを対象にしたIDEやCLIは両方をworkspaceへ読み込みます。

project間の依存関係はここに重複記載しません。TaskApi.Tests.csprojの <ProjectReference Include="..\TaskApi\TaskApi.csproj" />が、test projectをbuildする前にproduction projectが必要だと示します。
