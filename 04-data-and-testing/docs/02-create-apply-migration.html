EF Core migrationを作成してSQLiteへ適用する

今回の課題

  • 目安時間：30〜40分
  • 前提：DbContext、entity、primary key、foreign keyを説明できる
  • 目的：C#のEF model変更を、review可能なschema変更として生成・適用する流れを理解する

Codexが現在のTaskDbContextから初回migrationを生成し、SQLite databaseへ適用します。 学習者は生成されたUp、Down、model snapshotと、実際に作成されたtableを読みます。 migration commandを暗記することよりも、どのfileが変更計画で、どのfileが現在modelの基準で、 databaseが適用済みかを何で判定するのかを理解することが目的です。

migrationはdatabase schemaのversion管理

EF CoreのmodelはC# classとOnModelCreatingから組み立てられますが、modelを変更しただけでは既存databaseの tableは自動的に変わりません。稼働済みdatabaseにはdataがあり、column追加、foreign key変更、table削除などを 順序立てて適用する必要があります。

migrationは「以前のmodelから現在のmodelへdatabase schemaをどう変更するか」をC# codeとして記録します。 source controlへcommitできるため、変更内容をreviewし、環境ごとに同じ順序で適用できます。 migration fileはdatabaseそのものではなく、databaseを更新するためのversion付き手順です。

生成と適用は別の操作

dotnet tool run dotnet-ef migrations add InitialCreate \
  --project TaskApi/TaskApi.csproj \
  --output-dir Data/Migrations

migrations addはTaskDbContextの現在modelを読み、前回snapshotと比較してmigration sourceを生成します。 初回なので比較対象となるtableはなく、CategoriesとTasksを新規作成するcodeになりました。 この時点ではdatabaseへschema変更を適用していません。 

dotnet tool run dotnet-ef database update \
  --project TaskApi/TaskApi.csproj

database updateはconnection stringが示すdatabaseを開き、migration履歴tableを確認します。 未適用のmigrationだけを順番に実行し、成功後にmigration IDを__EFMigrationsHistoryへ記録します。 同じcommandを再実行しても、履歴に記録済みのmigrationは再適用されません。

三つの生成fileをどう読むか

20260812020906_InitialCreate.cs

人間が最初にreviewする変更手順です。Upは新しいversionへ進める操作、Downはこのmigrationを 戻す操作を表します。自動生成だから無条件に信用するのではなく、意図しないcolumn削除やdata lossがないかを確認します。 

protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.CreateTable(name: "Categories", /* ... */);
    migrationBuilder.CreateTable(name: "Tasks", /* ... */);
    migrationBuilder.CreateIndex(
        name: "IX_Tasks_CategoryId",
        table: "Tasks",
        column: "CategoryId");
}

table作成順はrelationに依存します。principalのCategoriesを先に作り、その後でforeign keyを持つdependentの Tasksを作ります。CategoryId検索やjoinに使えるindexも生成されています。

20260812020906_InitialCreate.Designer.cs

このmigrationを生成した時点のmodel metadataです。migration固有の情報としてEF Coreが利用します。 通常は手で編集せず、main migration fileと組にしてcommitします。

TaskDbContextModelSnapshot.cs

最新migration適用後にEF Coreが期待するmodelのsnapshotです。次にmigrations addを実行すると、 EF Coreはこのsnapshotと新しいTaskDbContext modelを比較して差分を生成します。 databaseを直接読み取って差分を作るのではない点が重要です。

C# modelがSQLite schemaへ変換された結果

CREATE TABLE "Tasks" (
    "Id" INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    "Title" TEXT NOT NULL,
    "IsCompleted" INTEGER NOT NULL,
    "CategoryId" INTEGER NULL,
    FOREIGN KEY ("CategoryId")
      REFERENCES "Categories" ("Id") ON DELETE SET NULL
);

CREATE INDEX "IX_Tasks_CategoryId"
ON "Tasks" ("CategoryId");

CategoryIdはC#でint?なのでSQLiteでもNULLを許します。 OnDelete(DeleteBehavior.SetNull)はON DELETE SET NULLになり、category削除時にtaskを残す方針が database constraintにも反映されています。boolのIsCompletedはSQLite providerによってINTEGERへ変換されます。

Titleの最大100文字やNameの最大50文字はmigration metadataには記録されています。 ただしSQLiteのTEXT型は長さをdatabase constraintとして強制しないため、providerごとのschema表現差も意識する必要があります。

__EFMigrationsHistoryが適用済みversionを示す

SELECT MigrationId, ProductVersion
FROM __EFMigrationsHistory;
20260812020906_InitialCreate|10.0.10

EF Coreはこの履歴を見て未適用migrationを判断します。migration sourceがGitに存在することだけでは、ある環境のdatabaseへ 適用済みとは証明できません。source control上のmigration一覧と、各databaseの履歴tableは別の状態です。

JPA / Hibernateとschema migrationの違い

JPA entityとHibernateのschema自動更新だけに任せるより、FlywayやLiquibaseでversion付きSQLを管理する考え方に近いです。 EF Core migrationsはORM modelから変更手順を生成できる点が統合されていますが、生成物をreviewして順番に適用する責任は同じです。

確認commandと観察結果

cd 04-data-and-testing
nix develop --command dotnet tool run dotnet-ef database update \
  --project TaskApi/TaskApi.csproj
nix develop --command sqlite3 TaskApi/tasks.db '.schema'
nix develop --command sqlite3 TaskApi/tasks.db \
  'SELECT MigrationId, ProductVersion FROM __EFMigrationsHistory;'
dotnet format TaskApi/TaskApi.csproj --verify-no-changes
dotnet build TaskApi/TaskApi.csproj

database updateはInitialCreateを適用しました。実DBにはCategories、Tasks、 IX_Tasks_CategoryId、__EFMigrationsHistoryが存在します。履歴にはmigration IDとEF Core version 10.0.10が1件記録されました。同じdatabase updateを再実行すると No migrations were applied. The database is already up to date.となり、適用済みmigrationが再実行されないことも確認しました。 formatterとbuildは成功し、buildのwarningとerrorはいずれも0件でした。

コードリーディング課題

  1. migrations addとdatabase updateは、それぞれ何を変更しますか。
  2. TaskDbContextModelSnapshotは、次回migration生成時に何と何を比較するために使われますか。
  3. CategoryIdがNULL可能で、category削除時にNULLへ変わることは、migrationのどの記述に現れていますか。

生成と適用を区別し、model設定とschema変更codeを対応付けられれば完了です。
