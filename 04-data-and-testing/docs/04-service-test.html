サービス層を直接呼ぶテストを読む

今回の課題

  • 目安時間：35〜45分
  • 前提：DbContextの役割と、LINQがToListAsyncで実行されることを説明できる
  • 目的：HTTPを通さずサービスを直接呼び、検索条件・並び順・projectionを自動検証するテストを読めるようになる

Codexが、endpoint内にあったtask検索をTaskQueryServiceへ分離し、そのサービスをxUnitから直接呼ぶテストを 実装しました。学習者の作業はコードの手入力ではなく、production codeとtest codeの対応関係を読み、テストが何を保証し、 何を保証していないかを説明することです。

サービス層を直接テストする意味

変更前の検索処理はMinimal APIのendpoint内にありました。この形でも動作しますが、検索処理だけを確認したくてもHTTP requestを 作り、routingを通し、responseを読み取る必要があります。検索条件の誤りなのか、HTTP周辺の設定の誤りなのかも切り分けにくくなります。

今回はendpointを「入力をサービスへ渡し、結果をHTTP responseにする場所」へ細くし、database queryを TaskQueryServiceへ移します。テストはこのサービスをnewで生成して直接呼びます。これによりrouting、model binding、 JSON serializationを対象外にし、completed=falseなら未完了taskだけをID順に返す、というサービスの振る舞いへ集中できます。

ただし、このテストはSQLiteとEF Coreも実際に動かします。外部database serverには接続しませんが、純粋なbusiness logicだけを isolationした厳密なunit testではなく、サービスとdatabase providerを組み合わせた小さなcomponent testに近い構成です。 repositoryをmockすればさらに狭いunit testにできますが、今回はLINQがSQLiteでも翻訳・実行できることを保証する価値を優先します。

xUnitとテストメソッドの形

xUnitは.NETで使われるtest frameworkの一つです。JavaのJUnitと同じく、属性を付けたmethodをtest runnerが発見して実行します。 [Fact]は引数を取らない一つのtest caseを表し、JUnit 5の@Testに近い役割です。 

[Fact]
public async Task GetTasksAsync_WhenCompletedIsFalse_ReturnsIncompleteTasksInIdOrder()

method名は「対象method」「条件」「期待結果」を並べています。C#のasync Task testでは、非同期処理を awaitできます。async voidにはせず、runnerが完了と例外を追跡できるTaskを返します。

test本体はArrange（前提を準備）、Act（対象を実行）、Assert（結果を検証）の順です。コメントに依存せず、空行と変数名で 三つの段階を読めるようにしています。

SQLiteのインメモリdatabase

Data Source=:memory:はfileではなくmemory上にdatabaseを作ります。各testで新しいconnectionを作るため、以前のtest dataや localのtasks.dbに左右されません。EnsureCreatedAsyncは現在のEF Core modelからtest用schemaを作り、その後に test専用dataを保存します。

重要なのはconnectionを開いたままにすることです。SQLiteのインメモリdatabaseはconnectionに属し、connectionを閉じるとdatabaseも 消えます。そのため、connectionを開く、schemaとdataを準備する、サービスを実行する、assertする、という一連の処理が終わるまで 同じconnectionを保持します。await usingによりtest methodを抜ける際には非同期に破棄されます。

実装コード：production側

04-data-and-testing/TaskApi/Services/TaskQueryService.cs

public sealed class TaskQueryService(TaskDbContext dbContext)
{
    public async Task<IReadOnlyList<TaskSummary>> GetTasksAsync(
        bool? completed,
        CancellationToken cancellationToken)
    {
        IQueryable<TaskItem> query = dbContext.Tasks.AsNoTracking();

        if (completed is not null)
        {
            query = query.Where(task => task.IsCompleted == completed.Value);
        }

        return await query
            .OrderBy(task => task.Id)
            .Select(task => new TaskSummary(
                task.Id,
                task.Title,
                task.IsCompleted,
                task.Category == null ? null : task.Category.Name))
            .ToListAsync(cancellationToken);
    }
}

primary constructorでrequest scopeのTaskDbContextを受け取ります。public methodの入力は任意の完了状態とキャンセル通知、 出力は取得済みの読み取り専用listです。IQueryableを呼び出し側へ返さず、このmethod内のToListAsyncで database I/Oまで完結させます。

04-data-and-testing/TaskApi/Program.cs

builder.Services.AddScoped<TaskQueryService>();

app.MapGet("/tasks", async (
    bool? completed,
    TaskQueryService taskQueryService,
    CancellationToken cancellationToken) =>
{
    var tasks = await taskQueryService.GetTasksAsync(completed, cancellationToken);
    return Results.Ok(tasks);
});

application起動時にserviceをscoped lifetimeとして登録します。requestが来るとASP.NET Coreが、そのrequest用の TaskQueryServiceとTaskDbContextを同じscopeから解決します。endpointはquery parameterと停止通知をserviceへ渡し、 取得結果を200 responseへ変換するだけになりました。

実装コード：test側

04-data-and-testing/TaskApi.Tests/TaskQueryServiceTests.cs

[Fact]
public async Task GetTasksAsync_WhenCompletedIsFalse_ReturnsIncompleteTasksInIdOrder()
{
    SQLitePCL.Batteries_V2.Init();

    await using var connection = new SqliteConnection("Data Source=:memory:");
    await connection.OpenAsync();

    var options = new DbContextOptionsBuilder<TaskDbContext>()
        .UseSqlite(connection)
        .Options;

    await using var dbContext = new TaskDbContext(options);
    await dbContext.Database.EnsureCreatedAsync();

    var learning = new TaskCategory { Name = "学習" };
    dbContext.Tasks.AddRange(
        new TaskItem { Id = 3, Title = "テストを読む", IsCompleted = false },
        new TaskItem { Id = 1, Title = "EF Coreを学ぶ", IsCompleted = false, Category = learning },
        new TaskItem { Id = 2, Title = "migrationを作る", IsCompleted = true });
    await dbContext.SaveChangesAsync();

    var service = new TaskQueryService(dbContext);

    var tasks = await service.GetTasksAsync(false, CancellationToken.None);

    Assert.Collection(
        tasks,
        task =>
        {
            Assert.Equal(1, task.Id);
            Assert.Equal("EF Coreを学ぶ", task.Title);
            Assert.Equal("学習", task.CategoryName);
        },
        task =>
        {
            Assert.Equal(3, task.Id);
            Assert.Equal("テストを読む", task.Title);
            Assert.Null(task.CategoryName);
        });
}

Arrangeでは、順序がわざと3, 1, 2になるようdataを追加しています。完了済みtaskも混ぜ、categoryあり・なしも用意します。 Actではfalseを渡してserviceを一度だけ呼びます。Assertでは要素数、順番、ID、title、category projectionをまとめて確認します。

Assert.Collectionはcollectionの要素数と順序を同時に検証します。ここでは二つの検証lambdaを渡しているため、結果が ちょうど2件で、1件目と2件目がそれぞれ期待どおりでなければ失敗します。完了済みID 2が混入した場合も、ID順でない場合も失敗します。

コードリーディング課題

次の3問へ、該当するコードを根拠に答えてください。

  1. このtestがHTTP endpointではなくTaskQueryServiceを直接呼ぶことで、検証対象から外しているASP.NET Coreの処理を二つ挙げてください。
  2. SQLite connectionをSaveChangesAsyncの直後に閉じると、その後のGetTasksAsyncは期待どおり動きません。なぜですか。
  3. 完了済みのID 2が誤って結果へ含まれた場合と、未完了taskがID 3、ID 1の順で返った場合に、Assert.Collectionが失敗する理由をそれぞれ説明してください。
