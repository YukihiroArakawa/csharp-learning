route・query・bodyのモデルbindingを読む

今回の課題

  • 目安時間：35〜45分
  • 前提：Minimal APIのGET / POST endpointを読める
  • 目的：HTTPリクエスト上の値がC#のparameterへ変換される規則を理解する

Codexがroute、query string、JSON bodyの3種類を受け取るendpointを実装します。 学習者は、HTTP上では文字列やbyte列として届く入力を、ASP.NET Coreがどの情報から int、bool?、recordへ変換するかをコードと実行結果から追います。

モデルbindingとは何か

HTTPリクエストには値を置ける場所が複数あります。resourceを特定するIDはpath、 一覧の絞り込み条件はquery string、作成するresourceの内容はbodyに置くのが一般的です。 しかしendpointのコードで毎回pathやbodyを手作業で解析すると、変換処理が本来の業務処理を隠してしまいます。

モデルbindingは、HTTPリクエストから値を取り出し、endpointのparameterが要求するC#型へ変換して、 ラムダを呼び出す仕組みです。endpointは、入力がHTTPのどのbyte位置にあったかではなく、 変換済みのid、completed、requestを使って処理を書けます。 

HTTPリクエスト
    ↓ 値の場所とparameterの型を調べる
ASP.NET Coreのモデルbinding
    ↓ 型変換済みの引数を渡す
endpointのラムダ
    ↓
タスクの取得・絞り込み・作成

bindingはMapGetやMapPostを登録した起動時ではなく、 実際のリクエストが届くたびに行われます。登録時にはroute patternとラムダのparameter情報が解析され、 runtimeには各リクエストの具体的な値が変換されます。

3種類の入力元

routeとqueryの値はURL上では文字列です。それでもparameterをintやbool?と宣言すると、 ASP.NET Coreが変換してからラムダを呼びます。bodyではContent-Type: application/jsonを手掛かりにJSONを読み、 property名とrecordのparameter名を対応付けます。

Spring MVCとの対応

Spring MVCにも同じ目的のbindingがあります。Springではannotationで入力元を明示することが多い一方、 Minimal APIはroute pattern、parameter名、parameter型から入力元を推論できます。 どちらも、controllerやendpointへ到達する前にHTTP入力をJava/C#の型へ変換する点は同じです。

実装したコード

query binding：GET /tasks?completed=false

app.MapGet("/tasks", (bool? completed) =>
{
    IEnumerable<TaskItem> result = tasks;

    if (completed is not null)
    {
        result = tasks.Where(
            task => task.IsCompleted == completed.Value);
    }

    return Results.Ok(result);
});

query stringのkey completedとparameter名が一致するため、その値がbindingされます。 bool?の疑問符はnullable value typeを表し、true、falseに加えて 「queryが指定されていない」状態をnullで表現できます。

queryがなければresultは全件のtasksのままです。値があれば completed.Valueを使い、完了状態が一致するtaskだけをLINQのWhereで残します。 queryはresourceを変えず、同じ一覧に対する任意の表示条件として働きます。

route binding：GET /tasks/1

app.MapGet("/tasks/{id:int}", (int id) =>
{
    var task = tasks.FirstOrDefault(task => task.Id == id);
    IResult result = task is null
        ? Results.NotFound()
        : Results.Ok(task);

    return result;
});

route patternの{id:int}は、pathのその位置をidとして取り出し、整数として解釈できるURLだけに endpointを一致させる指定です。parameterのint idは同じ名前なので、変換後の値を受け取ります。

FirstOrDefaultは一致する最初のtaskを返し、なければreference typeの既定値であるnullを返します。 三項演算子条件 ? true側 : false側で、見つからない場合は404 Not Found、見つかった場合は200 OKを選びます。 二つの具体的なresult型を一つの変数で扱うため、共通interfaceのIResultとして宣言しています。

body binding：POST /tasks

app.MapPost("/tasks", (CreateTaskRequest request) =>
{
    var task = new TaskItem(
        tasks.Count + 1,
        request.Title,
        false);

    tasks.Add(task);
    return Results.Created($"/tasks/{task.Id}", task);
});

complex typeであるCreateTaskRequestは、POSTのJSON bodyから作られます。 JSONのtitleがTitleへbindingされ、endpointには生成済みのrecordが渡されます。 endpointがbodyのstreamを開いたり、JSON parserを直接呼んだりする必要はありません。

bindingできることと、入力内容が業務上正しいことは別問題です。たとえば空titleも現在はrecordへ変換できます。 必須条件や文字数を検査して適切なstatusを返す処理は、次のvalidation課題で追加します。

# route binding
curl -i http://localhost:5164/tasks/1

# route constraintに一致しない値
curl -i http://localhost:5164/tasks/abc

# body binding
curl -i -X POST http://localhost:5164/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"モデルbindingを確認する"}'

  2. /tasks/abcがint idを受け取るラムダまで到達しないのは、route patternのどの指定によるものですか。
  3. body bindingに成功しても、空のtitleを別途validationする必要があるのはなぜですか。
