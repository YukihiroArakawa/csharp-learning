Minimal APIでGETとPOSTを作る

今回の課題

  • 目安時間：35〜45分
  • 前提：Generic Host、record、ラムダ式を読める
  • 目的：HTTPのGETとPOSTがMinimal APIのコードへ対応する流れを理解する

CodexがインメモリのタスクAPIを実装します。学習者はGETとPOSTを実行し、 HTTPリクエスト、endpoint、レスポンスの対応をコードから追います。 詳細なモデルbinding、validation、OpenAPIは後続課題で扱います。

最初に押さえる全体像

Web APIは、HTTPリクエストを受け取り、その内容に対応する処理を選び、 HTTPレスポンスを返すアプリケーションです。今回のAPIで選択条件になるのは、 HTTP methodとpathの組み合わせです。同じ/tasksでも、GETなら一覧取得、 POSTなら新規作成という別の処理になります。

MapGetやMapPostを呼んだ瞬間にGETやPOSTの処理が実行されるわけではありません。 アプリケーション起動時に「このmethodとpathのリクエストが来たら、このラムダを実行する」という対応表を登録します。 実際のラムダ実行は、app.Run()の後にクライアントからリクエストが届いた時です。 

起動時に登録する対応表

GET  /tasks  → tasksを一覧として返すラムダ
POST /tasks  → requestからTaskItemを作るラムダ

この対応表の一行をendpointと呼びます。endpointには、HTTP method、route、 実行する処理、最終的に返すレスポンスが含まれます。

Spring Bootとの違い

Spring MVCでは通常、@RestControllerのメソッドへrouteを割り当てます。 Minimal APIでは、Program.cs上でHTTP methodとrouteへ処理を直接割り当てます。 小さなAPIでは、起動設定からendpointまでを短いコードで追えます。

Spring MVCではcomponent scanがcontrollerを見つけ、annotationから対応表を構築します。 Minimal APIでは同じ対応関係をMapGetやMapPostのメソッド呼び出しとして明示します。 HTTPリクエストを受けるという役割は同じで、登録方法とコードの配置が異なります。

Spring BootMinimal API
@GetMapping("/tasks")app.MapGet("/tasks", ...)
@PostMapping("/tasks")app.MapPost("/tasks", ...)
ResponseEntity.created(...)Results.Created(...)

起動コードを上から読む

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

WebApplication.CreateBuilder(args)は、ASP.NET Coreアプリケーションの準備を始めます。 前フェーズのGeneric Hostと同じく、設定、ログ、DI、起動・停止管理を準備し、 さらにWebサーバーのKestrelやHTTP処理に必要な機能も組み込みます。

builder.Build()は、準備した設定から実行可能なWebApplicationを構築します。 変数appは、endpointを登録する対象であると同時に、最後に起動するアプリケーション本体です。 

app.MapGet(...);
app.MapPost(...);
app.Run();

MapGetとMapPostで先にendpointを登録し、最後のRunでWebサーバーを起動します。 Run後はリクエストを待ち続けるため、通常はその後にendpoint登録コードを書きません。

実装したコード

03-aspnet-core/MinimalApiSample/Program.cs

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

var tasks = new List<TaskItem>
{
    new(1, "Minimal APIのコードを読む", false)
};

app.MapGet("/tasks", () => Results.Ok(tasks));

app.MapPost("/tasks", (CreateTaskRequest request) =>
{
    var task = new TaskItem(tasks.Count + 1, request.Title, false);
    tasks.Add(task);

    return Results.Created($"/tasks/{task.Id}", task);
});

app.Run();

record TaskItem(int Id, string Title, bool IsCompleted);
record CreateTaskRequest(string Title);

データを保存する変数

var tasks = new List<TaskItem>
{
    new(1, "Minimal APIのコードを読む", false)
};

tasksは、アプリケーションのメモリ上に存在する変更可能なlistです。 最初からID 1のtaskを一件持っています。GETとPOSTのラムダは、外側で宣言された同じ tasks変数を参照します。このようにラムダが外側のlocal variableを利用することをclosureと呼びます。

new(1, ..., false)はtarget-typed newです。 左側のList<TaskItem>から型を判断できるため、new TaskItem(...)の型名を省略しています。

GET /tasksを読む

app.MapGet("/tasks", () => Results.Ok(tasks));

第1引数"/tasks"はrouteです。第2引数の() =>は引数を受け取らないラムダです。 GETリクエストが届くと、このラムダが現在のtasksをResults.Okへ渡します。

Results.Ok(tasks)はHTTP statusを200 OKにし、tasksをresponse bodyにします。 ASP.NET CoreがList<TaskItem>をJSON配列へserializeするため、 endpoint内でJSON文字列を手作業で組み立てる必要はありません。 

List<TaskItem>
    ↓ ASP.NET Coreがserialize
[{"id":1,"title":"...","isCompleted":false}]

POST /tasksを読む

app.MapPost("/tasks", (CreateTaskRequest request) =>
{
    var task = new TaskItem(tasks.Count + 1, request.Title, false);
    tasks.Add(task);

    return Results.Created($"/tasks/{task.Id}", task);
});

POSTではクライアントがContent-Type: application/jsonのbodyを送ります。 ASP.NET CoreはJSONのtitleをCreateTaskRequest.Titleへ対応付け、 作成したCreateTaskRequestをラムダのrequest引数へ渡します。 この変換をモデルbindingと呼びます。今回は自動変換が起きる場所だけ確認し、詳細は次の課題で扱います。

ラムダ内では、現在の件数に1を足してIDを作り、requestのtitleと未完了を示す falseからTaskItemを生成します。tasks.Add(task)が共有listを変更するため、 同じアプリケーションプロセスへ次のGETを送ると、新しいtaskも返されます。

Results.Okは200 OK、Results.Createdは201 Createdを返します。 Createdの第1引数は作成したresourceの場所を示すLocationヘッダー、 第2引数はJSON response bodyです。

201は「リクエストを処理できた」だけでなく「新しいresourceを作成した」ことを表します。 Location: /tasks/2は作成されたresourceの場所をクライアントへ知らせます。 今回はまだGET /tasks/{id}を実装していませんが、Locationには将来そのresourceを取得するURIを示しています。

二つのrecordの役割

record TaskItem(int Id, string Title, bool IsCompleted);
record CreateTaskRequest(string Title);

CreateTaskRequestはクライアントから受け取る入力の形です。新規作成時のIDと完了状態は サーバー側で決めるため、requestには含めません。TaskItemはサーバーが保持し、responseとして返すresourceの形です。 入力用と出力・保持用の型を分けることで、クライアントが勝手にIDや初期状態を指定する設計を避けています。

今回のデータが残る範囲

tasksはデータベースではなくプロセスのメモリにあります。そのため、同じ起動中のGETとPOSTでは共有されますが、 アプリケーションを停止して再起動すると初期の一件へ戻ります。今回の目的はHTTPとendpointの流れを読むことであり、 永続化は後のEF Coreフェーズで追加します。 

同じ起動中
GET（1件）→ POST（listへ追加）→ GET（2件）

再起動後
Program.csを最初から実行 → 初期データの1件へ戻る

また、tasks.Count + 1によるID生成や通常のList<T>は、同時に多数のPOSTを処理する実運用向けではありません。 今回はMinimal APIの最小構造を読むための一時的な実装です。

確認コマンド

最初の3コマンドは、ソースの整形、コンパイル、Webサーバー起動を順番に確認します。 dotnet runはリクエスト待受中そのまま動き続けるため、curlは別のterminalから実行します。 

cd 03-aspnet-core
dotnet format MinimalApiSample/MinimalApiSample.csproj --verify-no-changes
dotnet build MinimalApiSample/MinimalApiSample.csproj
dotnet run --no-build --project MinimalApiSample/MinimalApiSample.csproj

別のfishセッションから次を実行します。

curl -i http://localhost:5164/tasks

curl -i -X POST http://localhost:5164/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"POSTエンドポイントを確認する"}'

curl -i http://localhost:5164/tasks

curl -iの-iはresponse headerも表示するoptionです。 POSTでは-HでbodyがJSONであることを伝え、-dでJSON bodyを送ります。 statusだけでなくContent-TypeとLocationも確認します。

観察結果

# 最初のGET
HTTP/1.1 200 OK
[{"id":1,"title":"Minimal APIのコードを読む","isCompleted":false}]

# POST
HTTP/1.1 201 Created
Location: /tasks/2
{"id":2,"title":"POSTエンドポイントを確認する","isCompleted":false}

# POST後のGET
HTTP/1.1 200 OK
[{"id":1,...},{"id":2,...}]

POSTで作成したtaskが同じプロセス内のlistへ追加され、続くGETでは2件になりました。 フォーマット検証とビルドも成功し、警告・エラーは0件でした。

コードリーディング課題

  1. POSTが成功したとき、なぜ200ではなく201を返し、Locationヘッダーを付けるのでしょうか。
  2. POST後のGETで要素が増えるのは、どの変数を二つのendpointが共有しているためですか。

GETとPOSTの実測結果を確認し、上の2問を説明できれば完了です。
