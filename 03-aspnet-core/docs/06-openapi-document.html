Minimal APIからOpenAPI仕様を生成する

今回の課題

  • 目安時間：30〜40分
  • 前提：route、query、request body、responseの役割を説明できる
  • 目的：実装済みendpointのHTTP契約をOpenAPI JSONとして公開し、コードとの対応を読む

CodexがASP.NET Core標準のOpenAPI生成機能を追加します。学習者の作業はコードを手入力することではなく、 生成されたJSONを読み、route、入力、response schemaがどのC#コードから導かれたかを説明することです。

OpenAPIとは何か

OpenAPIはHTTP APIの使い方を、決められたJSONまたはYAML構造で記述する仕様です。 どのURLへどのHTTP methodでrequestを送り、どのparameterやbodyを渡し、どのようなresponseが返るかを 機械が読める形で表します。APIそのものを実行する仕組みではなく、APIの外部向け契約を記述する仕組みです。

人間向けの説明文だけでは、client code生成、入力補完、契約テストなどの自動処理には使いにくいという問題があります。 OpenAPI documentがあると、開発ツールは同じ契約情報を解釈できます。ただし、documentが存在するだけで 実装と契約が永久に一致するわけではありません。今回のASP.NET Core機能はendpoint metadataからruntimeに生成することで、 手書き仕様との差異を減らします。

ASP.NET Coreが仕様を組み立てる方法

Minimal APIを登録するとき、frameworkはURL文字列だけでなく、HTTP method、handlerの引数、戻り値なども endpoint metadataとして保持します。たとえばbool? completedは省略可能なquery parameter、 {id:int}とint idは整数のroute parameter、CreateTaskRequest requestは JSON request bodyとしてOpenAPI documentへ反映されます。

一方、handlerが共通interfaceのIResultを返すと、frameworkは実行時の分岐先まで静的には確定できません。 POSTが成功時に201、validation失敗時に400を返すことはmethod本体を読めば分かりますが、最初の生成結果では200だけが記録されました。 そこでProduces系metadataを明示し、実際のresponseとdocumentを一致させます。

AddOpenApiは、そのmetadataを集めてOpenAPI documentへ変換するserviceをDIへ登録します。 MapOpenApiは生成結果をHTTPで取得するためのendpointを登録します。前回と同じく、 serviceの準備とruntime endpointの公開は別の役割です。 

builder.Services.AddOpenApi(); // document生成serviceを準備

var app = builder.Build();

app.MapOpenApi();              // GET /openapi/v1.jsonを公開

既定のdocument名はv1なので、既定URLは/openapi/v1.jsonです。 今回はDevelopment環境だけで公開します。仕様に機密情報を直接含めるべきではありませんが、 endpoint一覧をProductionで誰に公開するかは運用上の判断が必要だからです。

Spring Bootとの比較

Spring Bootでspringdoc-openapiを導入し、controller method、annotation、DTOから /v3/api-docsを生成する構成に近いものです。ASP.NET CoreではMinimal APIのhandler signatureと endpoint metadataが主な情報源になり、標準packageのAddOpenApiとMapOpenApiでJSONを公開できます。

Spring Boot + springdocASP.NET Core
controller methodとannotationroute handlerとendpoint metadata
DTOのfield/propertyrecord/classのproperty
/v3/api-docs/openapi/v1.json

OpenAPI documentとSwagger UIは同じものではありません。OpenAPIは仕様とdocument形式であり、Swagger UIやScalarは そのdocumentを人間向け画面として表示する別toolです。今回は契約そのものを読むことが目的なので、UIは追加しません。

実装したコード

03-aspnet-core/MinimalApiSample/MinimalApiSample.csproj

<ItemGroup>
  <PackageReference Include="Microsoft.AspNetCore.OpenApi" Version="10.0.10" />
  <PackageReference Include="Microsoft.OpenApi" Version="2.7.5" />
</ItemGroup>

PackageReferenceは、このprojectをcompileするときに必要なNuGet packageを宣言します。 OpenAPIの型と拡張methodはMicrosoft.AspNetCore.OpenApiから提供されます。 applicationが依存するpackageなので、shell環境用のflake.nixではなくproject fileへ記録します。 復元時に推移依存のMicrosoft.OpenApi 2.0.0へ既知の脆弱性警告が出たため、 advisoryで修正済みとされる同じmajor versionの2.7.5を直接参照して安全なversionを選択しています。

03-aspnet-core/MinimalApiSample/Program.cs

builder.Services.AddProblemDetails();
builder.Services.AddOpenApi();

var app = builder.Build();

application構築前にOpenAPI生成serviceをDIへ登録します。この時点ではJSONを生成してresponseへ返してはいません。 後でOpenAPI endpointへrequestが届いたときに使える生成機能を準備しています。 

if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
}

application構築後にOpenAPI取得用endpointを登録します。DevelopmentならGET /openapi/v1.jsonが有効になり、 requestを受けた時点のendpoint metadataからdocumentが生成されます。Productionではこのrouteを登録しません。 

app.MapPost("/tasks", (CreateTaskRequest request) =>
{
    // validationと登録処理
})
.Produces<TaskItem>(StatusCodes.Status201Created)
.ProducesValidationProblem();

Produces<TaskItem>(201)は、成功時にstatus 201とTaskItem JSONを返す契約をmetadataへ追加します。 ProducesValidationProblem()は、validation失敗時の400 Problem Detailsを追加します。 これらはruntimeの分岐やresponseを作る命令ではありません。実際に何を返すかはhandler内の Results.CreatedとResults.ValidationProblemが決め、Producesは外部へ公開する説明を補います。

同様に、一覧GETには200とIEnumerable<TaskItem>、ID指定GETには200とTaskItemおよび404、 障害確認endpointには500 Problem Detailsを記録しています。実装を変更したらmetadataも合わせて変更する必要があります。

03-aspnet-core/MinimalApiSample/MinimalApiSample.http

GET {{host}}/openapi/v1.json
Accept: application/json

APIへ業務操作を要求するrequestではなく、API自身の契約documentを取得するrequestです。 responseのpathsでrouteを、各operationのparametersやrequestBodyで入力を、 responsesで返却内容を確認します。

確認方法と観察対象

cd 03-aspnet-core
dotnet restore MinimalApiSample/MinimalApiSample.csproj
dotnet format MinimalApiSample/MinimalApiSample.csproj --verify-no-changes
dotnet build MinimalApiSample/MinimalApiSample.csproj
dotnet run --no-build --project MinimalApiSample/MinimalApiSample.csproj

別のfishセッションからdocumentを取得します。

curl -s http://localhost:5164/openapi/v1.json

JSON全体を暗記する必要はありません。pathsに/tasksと/tasks/{id}が存在すること、 GETのcompletedが省略可能なboolean query parameterとして表現されること、POSTに CreateTaskRequestのrequest body schemaがあることを確認します。

観察結果

最初の生成結果はOpenAPI 3.1.1で、/tasks、/tasks/{id}、 Development限定の/diagnostics/failureがpathsへ出力されました。 completedはin: queryのbooleanでrequired: trueがなく、省略可能と表現されました。 idは必須のpath parameterかつinteger/int32、POST bodyは必須で CreateTaskRequest schemaを参照していました。

responseについては、metadata追加前はhandlerがIResultを返すため、実際の分岐にかかわらず200だけが生成されました。 Produces系metadataを追加した後、POSTの201と400、ID指定GETの200と404、 障害確認endpointの500がdocumentに現れました。200と201にはTaskItem schema、400には HttpValidationProblemDetails、500にはProblemDetailsも記録されました。 formatterとbuildは成功し、buildのwarningとerrorはいずれも0件でした。検証用APIも停止済みです。

コードリーディング課題

  1. AddOpenApiとMapOpenApiは、それぞれ「生成機能の準備」と「取得endpointの公開」のどちらですか。
  2. GET /tasksのcompletedが、OpenAPI上でquery parameterかつ省略可能になる根拠はどのC#コードですか。
  3. Producesを追加する前にPOSTの201と400がdocumentへ現れなかった理由と、Producesがruntime response自体を変更しない理由を説明してください。

生成されたJSONとコードを対応付け、上の3問を説明できれば完了です。
