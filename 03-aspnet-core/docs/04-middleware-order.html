middlewareの登録順と実行順を読む

今回の課題

  • 目安時間：35〜45分
  • 前提：HTTPリクエストがMinimal APIのendpointへrouteされることを説明できる
  • 目的：endpointの前後に共通処理を置き、middlewareの登録順が実行順を決めることを理解する

Codexがrequest timingとresponse headerのmiddlewareを実装します。学習者は一回のGETについて、 endpointへ向かう処理とresponseが戻る処理をログで追い、middlewareが単純な上から下の一方向処理ではないことを確認します。

middlewareとは何か

middlewareは、HTTPリクエストがendpointへ到達する途中に置く共通処理です。個々のendpointへ同じコードを繰り返さず、 request logging、例外処理、認証、response header追加などを複数のendpointへまとめて適用できます。

各middlewareは現在のHttpContextと、次の処理を呼ぶnextを受け取ります。 await next(context)より前に書いたコードはendpointへ向かう途中で実行され、 その後に書いたコードはendpointがresponseを作った後、呼び出し元へ戻る途中で実行されます。 

middleware Aの前半
  ↓
middleware Bの前半
  ↓
endpoint
  ↓
middleware Bの後半
  ↓
middleware Aの後半

これは関数Aが関数Bを呼び、関数Bがendpointを呼ぶ入れ子と同じです。endpointが終わると、 最も内側のBへ先に戻り、最後に外側のAへ戻ります。そのため、登録順はrequest側の順序だけでなくresponse側の逆順も決めます。

登録時とリクエスト時を区別する

app.Use(...)を実行するのはアプリケーション起動時です。この時点ではまだ具体的なHTTPリクエストはありません。 Useは「リクエストが来たらこのラムダを通す」というpipelineを登録します。

runtimeにGETやPOSTが届くと、登録済みpipelineがそのリクエストごとに実行されます。 contextには今回のrequestとresponseが入り、nextはpipelineの次の要素を表します。 

起動時
app.Use(A) → app.Use(B) → app.MapGet(...)
    ↓ pipelineを構築

リクエスト時
A → B → endpoint → Bへ戻る → Aへ戻る

Spring Bootとの対応

SpringのServlet Filter chainと近い役割です。Filterもchainの次を呼ぶ前後に処理を書けます。 ASP.NET CoreではmiddlewareをProgram.csのUse呼び出しとして並べるため、 pipelineの順序をコード上で直接確認できます。

実装したコード

request timing middleware

app.Use(async (context, next) =>
{
    var startedAt = Stopwatch.GetTimestamp();
    app.Logger.LogInformation(
        "Request timing middleware entering for {Method} {Path}",
        context.Request.Method,
        context.Request.Path);

    await next(context);

    var elapsed = Stopwatch.GetElapsedTime(startedAt);
    app.Logger.LogInformation(
        "Request timing middleware leaving with {StatusCode} after {ElapsedMilliseconds} ms",
        context.Response.StatusCode,
        elapsed.TotalMilliseconds);
});

using System.Diagnostics;によりStopwatchを短い名前で利用します。 GetTimestampで開始時点を記録し、endpointから戻った後にGetElapsedTimeで経過時間を求めます。 時計の現在日時を引き算するのではなく、経過時間測定用のAPIを使っています。

await next(context)の前ではmethodとpathを記録します。後ろでは、endpointが決めたstatusと処理時間を記録します。 一つのmiddlewareがrequestの入口とresponseの出口を挟むため、処理全体の時間を測れます。

response header middleware

app.Use(async (context, next) =>
{
    app.Logger.LogInformation(
        "Response header middleware entering");

    context.Response.Headers["X-Task-Api"] =
        "MinimalApiSample";

    await next(context);

    app.Logger.LogInformation(
        "Response header middleware leaving");
});

context.Response.Headersはresponse headerのcollectionです。 endpointへ進む前にX-Task-Apiを設定するため、GET、POST、404など、このmiddlewareを通るresponseへ共通して追加されます。

headerはresponse bodyの送信開始後には変更できない場合があるため、今回はnextより前に設定します。 後半のログはheader設定のためではなく、responseが内側から戻ってきた順番を観察するために置いています。

二つを並べたときの順序

timing middlewareを先に登録したので外側、header middlewareを後に登録したので内側になります。 実行ログは次の順番になるはずです。

  1. timing entering
  2. header entering
  3. endpointがresponseを作る
  4. header leaving
  5. timing leaving

もし二つのapp.Useの位置を交換すれば、外側と内側も交換されます。 つまりmiddlewareは内容だけでなく、どこへ登録するかもアプリケーションの挙動を構成します。

cd 03-aspnet-core
dotnet format MinimalApiSample/MinimalApiSample.csproj --verify-no-changes
dotnet build MinimalApiSample/MinimalApiSample.csproj
dotnet run --no-build --project MinimalApiSample/MinimalApiSample.csproj

別のfishセッションからheaderを含めてGET responseを確認します。

curl -i http://localhost:5164/tasks/1

curl側ではX-Task-Api: MinimalApiSampleを確認します。APIを起動したterminalでは、 enteringが登録順、leavingが逆順になっていることと、最後のtimingログに200と処理時間が含まれることを確認します。

観察結果

HTTP/1.1 200 OK
X-Task-Api: MinimalApiSample

Request timing middleware entering for GET /tasks/1
Response header middleware entering
Response header middleware leaving
Request timing middleware leaving with 200 after 24.944 ms

responseにはheader middlewareが設定したX-Task-Apiが含まれました。 request側のenteringは登録順、response側のleavingは逆順でした。 timing middlewareは最も外側で内側全体を挟んでいるため、endpointとheader middlewareを含む経過時間を記録しました。 フォーマット検証とビルドは成功し、警告・エラーは0件でした。

コードリーディング課題

  1. middlewareのenteringログは登録順なのに、leavingログが逆順になるのはなぜですか。
  2. timing middlewareがendpointを含む内側の処理時間を測れるのは、計測開始と終了をどこに置いているためですか。
  3. X-Task-Apiをawait next(context)より前に設定する理由は何ですか。
