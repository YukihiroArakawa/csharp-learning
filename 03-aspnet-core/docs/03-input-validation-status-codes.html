入力をvalidationしてHTTP statusを選ぶ

今回の課題

  • 目安時間：35〜45分
  • 前提：body bindingでJSONがCreateTaskRequestへ変換されることを説明できる
  • 目的：binding後の入力を検証し、成功・入力不正・resource不在をHTTP statusで区別する

Codexがtask titleの必須条件と最大文字数を実装します。学習者は、リクエストがC#型へ変換できることと、 アプリケーションが受け入れてよい値であることが別の判断であると理解し、各結果に対応するHTTP statusを読みます。

bindingとvalidationは役割が違う

body bindingは、JSONの構造を読み、CreateTaskRequestというC#の型へ変換します。 JSONのtitleが文字列なら、空文字や空白だけの文字列でも型としてはstringです。 そのため、型変換に成功しただけでは「taskのtitleとして利用できる」とは判断できません。

validationは、変換済みの値をアプリケーションのルールと比較する工程です。今回は、titleが空白だけではないこと、 100文字以内であることを確認します。違反していればlistを変更せず、どのフィールドがなぜ不正なのかをresponseで返します。 

JSON body
    ↓ body binding：C#型へ変換できるか
CreateTaskRequest
    ↓ validation：taskとして許される値か
有効 ─→ tasksへ追加 ─→ 201 Created
不正 ─→ 追加しない ─→ 400 Bad Request

validationはPOST endpointが呼ばれるたびにruntimeで行います。endpoint登録時に具体的なtitleはまだ存在しないため、 起動時にこの値を検査することはできません。

HTTP statusで結果の意味を伝える

HTTP statusは、クライアントがresponse bodyの文章を解析しなくても、処理結果の大分類を判断するための情報です。 今回のAPIでは、同じ4xxでも「入力が不正」と「対象が存在しない」を区別します。

status意味今回の例
200 OK取得に成功した存在するtaskをGET
201 Created新しいresourceを作成した有効なtitleでPOST
400 Bad Request送られた入力を受け入れられないtitleが空白または101文字以上
404 Not Found指定されたresourceが存在しない存在しないIDをGET

400と404は失敗原因が異なります。400ならクライアントは送信内容を修正して再試行できます。 404なら、指定したIDやresourceの存在を見直す必要があります。適切なstatusを返すことで、クライアントの分岐が安定します。

Spring Bootとの対応

Spring BootではDTOへBean Validationのannotationを付け、@Validで検証を起動する構成が一般的です。 今回はvalidationの実行順とresponseを直接読めるよう、追加ライブラリを使わず関数として記述します。 どちらの方法でも、binding後・状態変更前に入力を検査するという責務は同じです。

実装したコード

入力を検査する関数

static Dictionary<string, string[]> Validate(
    CreateTaskRequest request)
{
    var errors = new Dictionary<string, string[]>();

    if (string.IsNullOrWhiteSpace(request.Title))
    {
        errors["title"] = new[] { "Title is required." };
    }
    else if (request.Title.Length > 100)
    {
        errors["title"] = new[] {
            "Title must be 100 characters or fewer."
        };
    }

    return errors;
}

staticは、この関数が外側のtasksなどを参照せず、引数だけから結果を作ることを表します。 入力を受け取り、エラーを返すだけなので、validation中にlistを変更しません。

Dictionary<string, string[]>は、フィールド名をkey、複数のエラーメッセージを配列として持ちます。 new[] { ... }は要素からstring[]と推論される配列です。 現在はtitleに一つだけエラーを返しますが、形式としては一フィールドに複数の違反を表現できます。

IsNullOrWhiteSpaceはnull、空文字、空白文字だけの値をまとめて検出します。 else ifにすることで、必須違反の場合に長さ検査へ進まず、利用者にとって最も直接的なエラーだけを返します。

状態変更より先にvalidationする

var errors = Validate(request);
IResult result;

if (errors.Count > 0)
{
    result = Results.ValidationProblem(errors);
}
else
{
    var task = new TaskItem(
        tasks.Count + 1,
        request.Title,
        false);

    tasks.Add(task);
    result = Results.Created($"/tasks/{task.Id}", task);
}

return result;

endpointはまずValidateを呼びます。エラーが一件以上あれば Results.ValidationProblemを選び、tasks.Addのあるelse側へ進みません。 したがって、不正responseを返すだけでなく、不正なデータを保存しないことも保証します。

IResultはHTTP responseを書き出せる結果の共通interfaceです。 400を表すresultと201を表すresultは具体的な型が異なるため、共通のIResult変数へ代入して最後に返します。

ValidationProblemは400 statusとともに、errorsをフィールド別のJSONとして返します。 これによりクライアントはtitle欄の近くに該当メッセージを表示できます。

コードリーディング課題

  1. validationをtasks.Addより前に実行する必要があるのはなぜですか。
  2. 空白titleの400と、存在しないIDの404は、クライアントへそれぞれ何の違いを伝えますか。
  3. Validateをstaticにできるのは、この関数が何だけを使って結果を作るためですか。

正常・入力不正・resource不在を実測し、上の3問を説明できれば完了です。
