Controller APIを読み、Minimal APIと使い分ける

今回の課題

  • 目安時間：35〜45分
  • 前提：Minimal APIのroute、binding、validation、responseを読める
  • 目的：同じHTTP APIがController形式ではどこに記述されるかを追い、採用判断を説明できる

CodexがGET、ID指定GET、POSTを持つControllerApiSampleを実装します。学習者は、起動時の登録、 classとmethodに付いたattribute、action methodの引数と戻り値を実行順に読みます。 Controllerの構文を暗記するのではなく、Minimal APIで既に理解したroute、binding、validation、responseとの対応を探します。

Controller形式とは何か

Minimal APIではProgram.csのMapGetやMapPostが、routeとhandlerを直接結び付けます。 Controller形式では、ControllerBaseを継承したclassのpublic methodをactionとして使い、attributeで HTTP method、route、binding元、response metadataを宣言します。

requestが来るたびにASP.NET Coreが対象ControllerをDIから生成し、routeに一致するactionを呼びます。 Controller classそのものがserverを起動するわけではありません。AddControllersがMVCのserviceを準備し、 MapControllersがattributeからendpointを作ることでpipelineへ参加します。

起動時の準備とruntimeの公開

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers();

var app = builder.Build();

app.MapControllers();

AddControllersはController discovery、model binding、validation、formatterなどのMVC serviceをDIへ登録します。 これは起動時の準備です。MapControllersは発見したControllerのattribute routeをendpointとして公開します。 前に学んだAddOpenApiとMapOpenApiと同様に、serviceの準備とendpointの公開は別の段階です。

attributeを上から読む

[ApiController]
[Route("controller/tasks")]
public sealed class TasksController : ControllerBase

C#の[...]はattributeです。classやmethodなどへmetadataを付け、frameworkがreflectionなどを通じて読み取ります。 Java annotationに近い構文です。ApiControllerはこのclassをHTTP API向けControllerとして扱い、binding元の推論や model validation失敗時の自動400 responseなどを有効にします。

Route("controller/tasks")はclass内の全actionに共通するroute prefixです。 ControllerBaseはviewを描画しないAPI Controller向けbase classで、Ok、NotFound、 CreatedAtRouteなどのresponse helperを提供します。 

[HttpGet("{id:int}", Name = nameof(GetById))]
public ActionResult<TaskItem> GetById(int id)

class側routeとmethod側routeを結合して、GET /controller/tasks/{id:int}になります。 routeにあるidと同名の単純型引数へ値がbindingされます。ActionResult<TaskItem>は、成功時の TaskItemだけでなく、NotFound()など別statusのaction resultも返せる型です。

[ApiController]によるvalidationの位置

public sealed record CreateTaskRequest(
    [Required, StringLength(100)] string Title);

primary constructorのTitle parameterに、Data Annotationsのvalidation attributeを付けています。 Requiredはnullを拒否し、StringLength(100)は最大100文字に制限します。 Controllerがrecordを検証するときはconstructor parameterのmetadataを読みます。生成されるpropertyへ property:でattributeを付けるとvalidation metadataとして使われないため、parameterへ直接付けます。 

[HttpPost]
public ActionResult<TaskItem> Create([FromBody] CreateTaskRequest request)
{
    // validation成功時だけ実行される
}

FromBodyはJSON request bodyから引数を構築することを明示します。binding後、ApiControllerがvalidationを実行し、 不正ならactionを呼ばずに400 Validation Problem Detailsを返します。そのため、今回のaction内には if (!ModelState.IsValid)を書いていません。

Data Annotationsだけでは空白文字だけのtitleを業務上無効とする判断までは表現していません。 Controller形式でも、型としてbindingできることと業務上有効であることは別であり、必要ならcustom validationやservice層で補います。

CreatedAtRouteがLocationを組み立てる

return CreatedAtRoute(
    nameof(GetById),
    new { id = task.Id },
    task);

POST成功時は201 Createdを返し、名前を付けたGetById routeと新しいIDからLocation headerを生成します。 第一引数はroute名、第二引数のanonymous objectはroute parameter、第三引数はresponse bodyです。 URL文字列を直接組み立てないため、route template変更時の追従箇所を減らせます。

Minimal APIとの対応

関心事Minimal APIController API
service準備通常は追加不要AddControllers
endpoint公開MapGet / MapPostMapControllers + attribute
routeMapGet("/tasks/{id:int}", ...)[Route] + [HttpGet]
handlerdelegate / methodControllerのaction method
responseResults.OkなどOkなどのController helper
metadataProducesなどのmethod chainProducesResponseType attribute

両形式とも同じrouting、middleware、DI、認証認可などASP.NET Core基盤の上で動きます。 Controllerだけが「本格的なAPI」でMinimal APIが試作用、という区別ではありません。

どう使い分けるか

.NET 10の公式方針では、新規HTTP APIはまずMinimal APIが推奨されています。記述量が少なく、routeと処理の対応を近くに置け、 認証認可やOpenAPIなど通常のAPI機能にも対応するためです。小規模service、機能単位で整理されたendpoint、 既にMinimal APIを採用しているprojectでは自然な選択です。

Controller形式は、既存projectがMVC規約で統一されている場合、IModelBinderProviderによるbinding拡張、 IModelValidatorによる高度なvalidation、application model、application parts、ODataなどController/MVC固有機能が 必要な場合に選びます。class・attribute中心の構造をteam規約として重視する場合にも候補になります。

endpoint数が多いという理由だけでControllerへ変える必要はありません。Minimal APIもroute groupや別method・別fileへ分割できます。 逆に、既存Controller projectを「新しい形式だから」という理由だけでMinimal APIへ全面移行する必要もありません。 プロジェクトの規模、既存規約、必要なframework機能を基準に選びます。

Spring Bootとの比較

Controller形式はSpring MVCの@RestControllerにかなり近い読み方ができます。 class-level routeとmethod-level routeを結合し、method parameterへrequest値をbindingし、戻り値をHTTP responseへ変換します。

確認方法と観察対象

cd 03-aspnet-core
dotnet format ControllerApiSample/ControllerApiSample.csproj --verify-no-changes
dotnet build ControllerApiSample/ControllerApiSample.csproj
dotnet run --no-build --project ControllerApiSample/ControllerApiSample.csproj

ControllerApiSample.httpまたはcurlで、一覧GET、ID指定GET、正常POST、titleがnullのPOSTを送ります。 正常POSTでは201とLocation、validation失敗ではaction内に分岐を書かなくても400 Problem Detailsになることを確認します。

一覧GETは200と絞り込まれたJSON配列を返しました。正常POSTは201、作成したTaskItem、 Location: http://localhost:5174/controller/tasks/3を返しました。titleがnullのPOSTでは Create actionの本体へ入らず、400とapplication/problem+json、 Title field is requiredというvalidation errorが返りました。 formatterとbuildは成功し、buildのwarningとerrorはいずれも0件でした。検証用APIも停止済みです。

コードリーディング課題

  1. AddControllersとMapControllersは、それぞれ準備と公開のどちらですか。
  2. titleがnullのPOSTでCreate actionを実行せず400を返せるのは、どのattributeとvalidation metadataがあるためですか。
  3. 新規の単純なHTTP APIと、MVC固有の高度なmodel binding拡張が必要なAPIでは、それぞれどちらの形式を第一候補にしますか。

Controllerコードをrequestの入口からresponseまで追い、使い分けの理由を説明できれば完了です。
