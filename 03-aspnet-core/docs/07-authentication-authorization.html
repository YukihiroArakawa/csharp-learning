認証・認可とrole・policyを区別する

今回の課題

  • 目安時間：25〜35分
  • 前提：middleware pipelineとHTTP status codeを説明できる
  • 目的：認証と認可を処理順に区別し、roleとpolicyを要件に応じて選べる

今回はauthentication providerを実際には追加しません。JWTを安全に検証するにはissuer、audience、署名鍵、 token発行元などの実環境情報が必要であり、それらを持たない偽のlogin処理には実務上の学習価値が低いためです。 代わりに、現場の認証設定を読んだときに「誰であるかの確定」と「その人に操作を許すかの判断」を追跡できることを目指します。

認証と認可は別の質問に答える

認証（authentication）は、requestを送った主体が誰であるかを確認する処理です。JWT bearer tokenなら署名、issuer、audience、 有効期限などを検証し、成功するとuser ID、role、その他の属性をclaimとして持つClaimsPrincipalを作ります。 この段階では、特定endpointの操作を許可するかまでは決めません。

認可（authorization）は、認証によって得られたuser情報とendpointの要件を比較し、その操作を許可するか判断します。 「login済みなら閲覧可能」「Administrator roleだけ削除可能」「自分が所有するtaskだけ更新可能」などが認可です。 認可は通常、認証結果を材料にするため、pipeline上でも認証の後に評価されます。

401と403から失敗箇所を読む

保護されたAPIでcredentialがない、またはtokenを正しく検証できずuserを特定できない場合は、通常401 Unauthorizedになります。 名前にUnauthorizedとありますが、実務上は「まだ有効な認証が成立していない」と読みます。JWT bearer schemeなら、 clientへ必要な認証方式を知らせるWWW-Authenticate: Bearer headerを返すことがあります。

認証は成功したものの、必要なroleやpolicy requirementを満たさない場合は403 Forbiddenです。 serverは誰であるかを把握していますが、そのuserには操作を許していません。したがって、403をtoken未提示の問題として直したり、 401を権限不足として扱ったりすると、調査箇所を間違えます。

結果認証状態意味
401 Unauthorized成立していない有効なcredentialを提示して認証する必要がある
403 Forbidden成立しているidentityは分かるが、この操作の認可要件を満たさない

ASP.NET Core 10では、Minimal APIなど既知のAPI endpointにcookie認証を使った場合も、認証・認可失敗をlogin画面へのredirectではなく 401または403として返すのが既定です。browser pageとprogrammatic APIでは望ましい失敗表現が異なるためです。

roleは「所属」を使う単純な認可

roleは、認証済みuserがAdministrator、Manager、Operatorなどの集合に所属するかを確認します。 endpointの許可条件が組織上の役割だけで安定して表せる場合は、簡潔で読みやすい方法です。 

app.MapDelete("/tasks/{id:int}", DeleteTask)
    .RequireAuthorization(policy =>
        policy.RequireRole("Administrator"));

この例はAdministrator roleを持つuserだけに削除を許します。role名は認証時に作られたidentityのrole claimと照合されます。 ただしroleへ業務条件を詰め込み始めると、AdministratorInTokyoDuringBusinessHoursのような不自然なroleが増えます。 roleは「何者として所属しているか」を表す用途に留めます。

policyは「満たすべき条件」に名前を付ける

policyは一つ以上のauthorization requirementをまとめた名前付きルールです。roleだけでなく、特定claim、認証済みであること、 custom handlerによる業務判断などを組み合わせられます。endpoint側は実装詳細ではなく、必要なpermissionの意味を表すpolicy名を指定します。 

builder.Services.AddAuthorizationBuilder()
    .AddPolicy("CanManageTasks", policy =>
        policy.RequireClaim("permission", "tasks.manage"));

app.MapPost("/tasks", CreateTask)
    .RequireAuthorization("CanManageTasks");

CanManageTasksは、permission=tasks.manageというclaimを要求します。将来、Manager roleも許可する、 tenant条件を追加するなど要件が変わっても、endpointは同じpolicy名を参照したまま、中央の定義を変更できます。

「本人が所有するtaskだけ更新可能」のように対象resourceの内容を見なければ判断できない場合は、role文字列だけでは足りません。 resource IDから取得したtaskと現在userをauthorization handlerで比較するresource-based authorizationが適しています。

roleとpolicyの使い分け

要件選択理由
管理画面はAdministratorだけrole、またはroleを包むpolicy所属だけで判断できる
tasks.manage permissionを持つuserpolicyroleではなくclaim条件を表す
18歳以上かつ本人確認済みpolicy複数requirementを組み合わせる

小さな固定要件ならrole指定で十分です。一方、業務上のpermission、複数条件、resourceとの関係を表すならpolicyを優先します。 policy内部でRequireRoleを使うこともできるため、roleとpolicyは完全な二者択一ではありません。

Spring Securityとの対応

Spring Securityでも、authenticationがAuthentication objectを作り、authorizationがrequestやmethodの access ruleを評価します。ASP.NET CoreのClaimsPrincipalは認証済み主体を表し、endpointの RequireAuthorizationはSpring Securityのrequest authorizationや@PreAuthorizeに近い役割です。
