例外responseをProblem Detailsへ統一する

今回の課題

  • 目安時間：35〜45分
  • 前提：middlewareが後続pipelineを包み、例外が外側へ伝わることを読める
  • 目的：未処理例外を一か所で捕捉し、クライアントへ一定形式の500 responseを返す

CodexがASP.NET Core標準のProblem Details serviceと例外処理middlewareを追加します。 学習者は、endpointごとにtry/catchを書かなくても、pipelineの外側で例外を捕捉し、 HTTP APIとして解釈できるJSON responseへ変換できることを確認します。

未処理例外をそのままにすると何が困るか

endpointやその下流のserviceで想定外の例外が発生した場合、クライアントはC#の例外オブジェクトを直接扱えません。 クライアントが必要なのは、HTTPとして失敗したことを示すstatus、エラーの種類、人間向けの概要、 問い合わせ時に使える追跡情報などです。

endpointごとに異なるJSONを返すと、クライアントはendpointごとの分岐を持つことになります。 また、stack traceや内部パスをresponseへそのまま含めると、実装詳細を外部へ漏らす危険があります。 そこで例外responseの作成をpipelineの一か所へ集約します。 

endpointで例外
    ↓ 外側へ伝播
例外処理middlewareが捕捉
    ↓ ログへ例外を記録
Problem Detailsを生成
    ↓
HTTP 500 + application/problem+json

Problem Detailsとは何か

Problem Detailsは、HTTP APIのエラー情報を共通のフィールドで表す形式です。 成功responseの業務データとは別に、失敗の概要を機械と人間の両方が読みやすい形で返します。 

{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.6.1",
  "title": "An error occurred while processing your request.",
  "status": 500
}
field役割
type問題の種類を識別するURI
title問題の短い概要
statusHTTP status code
detail必要な場合に付ける具体的説明
instance問題が起きた個別requestの識別情報

すべてのfieldが常に必要なわけではありません。今回の500 responseでは内部例外のmessageやstack traceを返さず、 一般化されたtitleを返します。詳細な原因はサーバー側のログで調査します。

service登録とmiddleware登録の役割

AddProblemDetailsとUseExceptionHandlerは似た名前ではありませんが、別の役割を持ちます。 前者はProblem Detailsを書くserviceをDIへ登録し、後者はrequest pipelineで例外を捕捉します。 

builder.Services.AddProblemDetails(); // response生成機能をDI登録

var app = builder.Build();

app.UseExceptionHandler();           // request pipelineへ登録

起動時にはserviceとpipelineを構築するだけです。runtimeに例外が発生すると、 UseExceptionHandlerが捕捉し、登録済みのProblem Details serviceを使ってresponseを書きます。

例外処理middlewareを既存のtiming middlewareより先に登録するのは、後続のmiddlewareとendpointをまとめて包むためです。 内側から伝わる例外を最も外側で受け止められます。

Spring Bootとの対応

Spring Bootで@ControllerAdviceと@ExceptionHandlerを使い、複数controllerの例外responseを 一か所へまとめる考え方に対応します。ASP.NET Coreでは例外処理middlewareをpipelineの外側へ置き、 Problem Details serviceへresponse形式を任せます。

Spring BootASP.NET Core
@ControllerAdviceUseExceptionHandler
共通error DTOProblem Details
server logへ例外Exception Handlerが例外をlog

実装したコード

Problem Details serviceを登録する

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddProblemDetails();

var app = builder.Build();

builder.ServicesはDI登録先です。AddProblemDetailsにより、HTTP errorをProblem Detailsとして 書き出す標準serviceが利用可能になります。この行だけでは例外を捕捉せず、response生成の能力を準備します。

例外処理middlewareを最初に登録する

app.UseExceptionHandler();

app.Use(/* request timing middleware */);
app.Use(/* response header middleware */);

UseExceptionHandlerが最初なので、後から登録したmiddlewareとendpointの外側になります。 nextの内側で例外が起きると、通常のresponseへ戻る代わりに例外が外へ伝わり、 Exception Handlerが500 responseへ変換します。

Development限定の検証endpoint

if (app.Environment.IsDevelopment())
{
    app.MapGet("/diagnostics/failure", () =>
    {
        throw new InvalidOperationException(
            "Development-only failure for Problem Details verification.");
    });
}

正常な業務endpointへ意図的な障害条件を混ぜず、例外処理を観察するためのendpointをDevelopment環境だけに登録します。 IsDevelopment()は現在のenvironment名を確認します。Productionではこのroute自体が登録されません。

throwは例外を発生させ、その時点で通常のendpoint処理を中断します。 endpoint内でcatchしないため、例外はmiddleware pipelineの外側へ伝わります。 このendpointの目的は今回の共通例外処理を再現可能に検証することだけです。

responseでは500、application/problem+json、type、title、statusを確認します。 API側では例外がログに記録される一方、responseには内部messageやstack traceが含まれないことを確認します。

観察結果

HTTP/1.1 500 Internal Server Error
Content-Type: application/problem+json

{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.6.1",
  "title": "An error occurred while processing your request.",
  "status": 500,
  "traceId": "00-4eea...-00"
}

クライアントには一般化されたtitleと追跡用のtraceIdが返りました。 検証用の例外message、ソースパス、stack traceはresponseに含まれず、Exception Handlerのserver logだけに記録されました。 

Request timing middleware entering for GET /diagnostics/failure
Response header middleware entering
fail: Microsoft.AspNetCore.Diagnostics.ExceptionHandlerMiddleware
System.InvalidOperationException:
Development-only failure for Problem Details verification.

例外がawait next(context)から外側へ伝わったため、timingとheader middlewareのleavingログは実行されませんでした。 さらに外側にあるException Handlerが例外を捕捉して500 responseへ変換しました。 フォーマット検証とビルドは成功し、警告・エラーは0件でした。APIプロセスも停止済みです。

コードリーディング課題

  1. AddProblemDetailsとUseExceptionHandlerは、それぞれ何を登録していますか。
  2. 例外処理middlewareをtiming middlewareより先に登録する理由は何ですか。
  3. 例外messageやstack traceを500 responseへそのまま含めない理由は何ですか。

500 responseとserver logを実測し、上の3問を説明できれば完了です。
