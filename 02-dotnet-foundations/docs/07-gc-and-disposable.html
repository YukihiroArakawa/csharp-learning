GCとIDisposableの責務を区別する

今回の課題

  • 目安時間：20〜30分
  • 前提：usingとIDisposableの基本構文を読める
  • 目的：managed memoryの回収と、外部resourceの解放を別の責務として判断できる

この項目ではruntime内部を再現するためのコードは書きません。実務で必要なのはGCのalgorithmを実装することではなく、 objectを使い終えたときにGCへ任せてよいのか、Disposeを確実に呼ぶ必要があるのかを判断することだからです。 説明を読んだ後、三つの状況についてresourceの終了時点を説明します。

二つの責務を分けて考える

.NETのGC（garbage collector）は、applicationが作ったmanaged objectのうち、到達できなくなったものが使っていた managed heap上のmemoryを再利用可能にします。通常のclass instance、配列、文字列などについて、開発者がmemoryを 手動でfreeする必要がないのはGCがあるためです。

しかしapplicationが扱うresourceはmemoryだけではありません。file handle、socket、database connection、OS handleなどは、 process外部またはOS側の限られたresourceと結び付いています。C#のwrapper object自体はmanaged objectでも、その背後にある resourceは「objectが不要になったら、いつかGCが気付けばよい」とは限りません。fileを閉じる、connectionをpoolへ返す、 bufferをflushするといった終了処理には、明確な実行時点が必要です。

GCは「不要になった瞬間」の通知ではない

local variableがscopeを抜けたことと、そのobjectのmemoryが直ちに回収されることは同じではありません。 runtimeはallocation量や世代などを見てGCを実行します。そのため、objectが到達不能になってから回収されるまでの時間を application codeは通常保証できません。GCが一度も必要にならないままprocessが終了する場合もあります。

finalizerを持つ型では、GCが到達不能を検出した後にfinalizer実行を待つ段階も入ります。finalizerはresource漏れに対する 最終的な安全網にはなりますが、「このmethodを抜ける前にfileを閉じる」という決定的なlifetime管理には使えません。 application developerが通常行うべきなのはGCやfinalizerを強制することではなく、公開されたDispose契約を守ることです。

IDisposableは終了処理を呼び出せるという契約

IDisposableを実装する型は、利用者へ「使い終えた時点でDisposeを呼んでください」と伝えています。 Disposeが必ずOS handleを直接解放するとは限りません。内部のstreamを閉じる、connectionをpoolへ戻す、 timerを停止する、保持している別のIDisposableを破棄するなど、型が所有するresourceの終了処理全体を表します。 

using (var stream = File.OpenRead(path))
{
    // streamを利用する
} // scopeを抜けるとDisposeが呼ばれる

usingは例外が起きてもDisposeが呼ばれるようにする構文です。重要なのはmemoryを早く消すことではなく、 resourceを所有するscopeをコードで明確にし、その終了時にcleanupを保証することです。

Dispose後もwrapper objectのmanaged memoryが即座に消えるわけではありません。終了処理が済んだobjectは、 その後到達不能になればGCの対象になります。したがって、DisposeとGCは同じobjectのlifetime上で順番に関わることはあっても、 同じ処理ではありません。

Disposeするかは「誰が所有しているか」で判断する

IDisposableを見つけたら無条件にその場でDisposeすればよいわけではありません。 resourceを生成してlifetimeを決める側が、通常はその終了にも責任を持ちます。method内で自分が File.OpenReadしたstreamはそのmethodが所有するため、usingで閉じるのが自然です。

一方、DI containerから受け取ったserviceはcontainerが所有していることがあります。その場合、利用側が勝手にDisposeすると、 同じscope内の別処理が使うserviceまで終了させる可能性があります。ASP.NET Coreのscoped serviceならrequest scopeの終了時に containerがDisposeします。大切なのは型名だけで判断せず、生成元とlifetime boundaryを確認することです。

Javaとの比較

JavaのGCと.NETのGCは、どちらも到達不能なmanaged objectのmemoryを自動管理します。 Javaでもfileやdatabase connectionをGC任せにせず、AutoCloseableをtry-with-resourcesで閉じます。 C#のIDisposableとusingは、実務上ほぼ同じ判断に対応します。
