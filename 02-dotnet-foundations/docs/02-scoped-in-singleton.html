singletonからscopedを直接参照できない理由

この学習項目について

  • 目安時間：15分
  • 対象：02-dotnet-foundations/HostedWorker
  • 種類：一時的なエラー再現＋コードレビュー

長く生存するsingletonが、短いスコープで破棄されるべきscoped serviceを保持すると、 scoped serviceをいつ破棄すべきか決められません。このlifetimeの不整合を captive dependency と呼びます。

寿命の不整合

AddHostedService<Worker>() で登録されたWorkerはsingletonです。 アプリケーション起動時に一度作られ、停止まで生存します。一方、 ScopedId は一つのスコープが終わると破棄されるべきサービスです。

観察したエラー

Codexが検証のため、Workerのprimary constructorへ ScopedId scopedId を一時的に追加しました。 

public class Worker(
    ILogger<Worker> logger,
    IServiceScopeFactory scopeFactory,
    ScopedId scopedId) : BackgroundService

Development環境でHostを起動すると、DIコンテナはサービスを構築する前に lifetimeの不整合を検出しました。 

Cannot consume scoped service 'HostedWorker.ScopedId'
from singleton 'Microsoft.Extensions.Hosting.IHostedService'.

エラーは Worker.ExecuteAsync の実行中ではなく、 builder.Build() でDIコンテナを構築するときに発生しました。 不正な依存関係を処理開始前に検出するためです。

正常な設計

singletonのWorkerには、scoped serviceそのものではなく IServiceScopeFactory を注入します。処理単位でスコープを作り、 そのスコープの ServiceProvider からscoped serviceを取得します。 

using var scope = scopeFactory.CreateScope();

var scopedId = scope.ServiceProvider
    .GetRequiredService<ScopedId>();

using の範囲を抜けるとスコープが破棄され、スコープ内で生成された disposableなサービスもまとめて破棄されます。Springでsingleton beanから request-scoped beanを直接保持せず、スコープを意識したproxyやproviderを介する考え方に近いものです。

変更対象

正常なC#コードへの永続的な変更はありません。一時的に 02-dotnet-foundations/HostedWorker/Worker.cs を変更してエラーを観察し、 観察後に元の正常な実装へ戻しました。

学習記録として、この 02-dotnet-foundations/docs/02-scoped-in-singleton.html だけを新規作成します。

検証結果

  • 直接注入時：Host構築に失敗し、期待したlifetime検証エラーを確認
  • 正常実装へ復元後：ソース差分が教材追加だけであることを確認

レビュー課題と完了条件

次の問いに答えてください。

  1. DIコンテナが直接注入を許可した場合、ScopedIdは実質的にどのlifetimeのように振る舞うでしょうか。
  2. IServiceScopeFactory を注入する方法では、scoped serviceをいつ破棄できるようになりますか。
