ホスト停止をCancellationTokenで処理へ伝える

今回の課題

  • 目安時間：25分
  • 前提：async / awaitとCancellationTokenの基本を読める
  • 目的：ホストの停止要求を、Workerから実際の待機処理まで伝播させて終了する

Codexが停止経路を明示したコードを実装します。学習者は、ホストから渡された 一つのtokenがどこまで伝わり、停止時の例外がなぜ障害扱いされないかを読みます。

停止要求の流れ

Generic Hostは停止を始めると、ExecuteAsyncへ渡した stoppingTokenをキャンセル状態にします。Workerはtokenを下流の 非同期処理へ渡します。待機中でもTask.Delayがすぐ中断されるため、 delay時間が終わるまで停止を待つ必要がありません。

Springの@PreDestroyは終了時のcallbackに近いのに対し、 CancellationTokenは実行中の非同期処理へ停止要求を伝播できます。 Javaのinterruptを確認しながら処理を終える考え方に近いですが、tokenを引数として明示的に渡します。

実装したコード

02-dotnet-foundations/HostedWorker/Worker.cs

await RunHeartbeatAsync(
    settings.DelayMilliseconds,
    stoppingToken);

呼び出し元のstoppingTokenをそのまま下流へ渡します。 Javaでメソッド引数を通じて処理条件を渡すのと同じく、依存関係がコード上に現れます。 

private async Task RunHeartbeatAsync(
    int delayMilliseconds,
    CancellationToken cancellationToken)
{
    var iteration = 0;

    try
    {
        while (!cancellationToken.IsCancellationRequested)
        {
            iteration++;
            logger.LogInformation(
                "Worker heartbeat {Iteration} at {OccurredAt}",
                iteration,
                DateTimeOffset.Now);

            await Task.Delay(delayMilliseconds, cancellationToken);
        }
    }
    catch (OperationCanceledException)
        when (cancellationToken.IsCancellationRequested)
    {
        logger.LogInformation(
            "Worker stopped after {IterationCount} heartbeat(s)",
            iteration);
    }
}

when (...)はcatch filterです。Javaのcatchには直接対応する構文がなく、 catchした後に条件を調べて再throwする処理に近いものです。 tokenが実際にキャンセルされた場合だけ、この例外を予定された停止として扱います。 別原因のOperationCanceledExceptionまで隠しません。

ループ条件だけでなくTask.Delayにもtokenを渡す点が重要です。 ループ条件だけでは、停止要求が待機中に来てもdelay完了まで反応できません。

確認コマンド

cd 02-dotnet-foundations
dotnet format HostedWorker/HostedWorker.csproj --verify-no-changes
dotnet build HostedWorker/HostedWorker.csproj
timeout --signal=TERM 3s \
  dotnet run --no-build --project HostedWorker/HostedWorker.csproj

timeoutが3秒後にSIGTERMを送り、Generic Hostが停止を開始します。 終了コード124はtimeoutによる停止を表すため、今回は停止ログと未処理例外の有無を確認します。

観察結果

Application is shutting down...
Worker stopped after 3 heartbeat(s)

SIGTERM後、待機中のTask.Delayがキャンセルされ、catch filterの処理へ移りました。 IterationCountを持つ停止ログが出力され、未処理例外はありませんでした。 ビルドは警告・エラーともに0件でした。

  2. catch filterでcancellationToken.IsCancellationRequestedを確認する理由は何ですか。

停止ログと未処理例外がないことを確認し、上の2問を説明できれば完了です。
