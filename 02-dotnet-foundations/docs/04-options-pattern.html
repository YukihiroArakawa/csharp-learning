Optionsパターンで設定を型安全に読む

今回の課題

  • 目安時間：25分
  • 前提：IConfigurationが複数の設定元を統合することを説明できる
  • 目的：文字列キーによる設定アクセスをC#の型へまとめ、起動時に検証する

CodexがOptionsパターンを実装します。学習者は、設定値がJSONから WorkerOptionsへ変換され、DIを通じてWorkerへ届く経路を読みます。

なぜ型へまとめるのか

configuration["Worker:DelayMilliseconds"] のようなアクセスは 戻り値が文字列で、キーのタイプミスもコンパイルでは検出できません。 Optionsパターンでは、設定を専用クラスへ変換します。利用側は intとして受け取れるため、変換処理や文字列キーを繰り返しません。

Spring Bootの @ConfigurationProperties(prefix = "worker") を付けた 設定クラスに近い仕組みです。

実装したコード

02-dotnet-foundations/HostedWorker/WorkerOptions.cs

public sealed class WorkerOptions
{
    public const string SectionName = "Worker";

    public string Message { get; init; } = string.Empty;

    public int DelayMilliseconds { get; init; }
}

constはコンパイル時に決まる定数です。 SectionNameへセクション名を一か所に集約します。 initは初期化時だけ値を設定でき、以後の不用意な変更を防ぎます。 Javaの設定用POJOまたはrecordに近い役割ですが、.NETの設定binderが public propertyへ値を設定できる形にします。

02-dotnet-foundations/HostedWorker/Program.cs

builder.Services
    .AddOptions<WorkerOptions>()
    .Bind(builder.Configuration.GetSection(WorkerOptions.SectionName))
    .Validate(options => !string.IsNullOrWhiteSpace(options.Message),
        "Worker:Message must not be empty.")
    .Validate(options => options.DelayMilliseconds is >= 100 and <= 60_000,
        "Worker:DelayMilliseconds must be between 100 and 60000.")
    .ValidateOnStart();
  • AddOptions<WorkerOptions>()：この設定型をDIへ登録する
  • Bind(...)：Workerセクションをpropertyへ対応付ける
  • Validate(...)：値が業務上許される範囲か検証する
  • ValidateOnStart()：設定ミスを実処理の途中ではなく起動時に検出する

options => ... はラムダ式で、Javaの options -> ... に対応します。 is >= 100 and <= 60_000 は値が範囲内か調べるrelational patternです。 数字中のアンダースコアは読みやすさのためで、値は60000です。

02-dotnet-foundations/HostedWorker/Worker.cs

using Microsoft.Extensions.Options;

IOptions<WorkerOptions> options

var settings = options.Value;

await Task.Delay(settings.DelayMilliseconds, stoppingToken);

ジェネリック型 IOptions<WorkerOptions> をDIで受け取り、 Valueから型付けされた設定を取得します。 DelayMillisecondsは既にintなので、Worker内で文字列から変換しません。

確認コマンド

cd 02-dotnet-foundations
dotnet format HostedWorker/HostedWorker.csproj --verify-no-changes
dotnet build HostedWorker/HostedWorker.csproj
timeout 3s dotnet run --no-build --project HostedWorker/HostedWorker.csproj

env Worker__DelayMilliseconds=50 \
  dotnet run --no-build --project HostedWorker/HostedWorker.csproj

通常起動ではメッセージと1000 msがログに出ます。 二つ目は許容範囲外のため、Workerの反復処理へ入る前にOptions validationで起動が失敗する想定です。

観察結果

# 通常設定（終了コード124はtimeoutによる停止）
Configured message: appsettings.jsonからのメッセージ; delay: 1000 ms

# Worker__DelayMilliseconds=50（終了コード134）
Microsoft.Extensions.Options.OptionsValidationException:
Worker:DelayMilliseconds must be between 100 and 60000.

通常設定ではHostが起動しました。不正値では Worker running atが一度も出る前にHost起動が失敗しました。

コードリーディング課題

  1. WorkerOptions.DelayMillisecondsがintであることにより、Worker側で不要になった処理は何ですか。
  2. ValidateOnStart()を付けると、設定ミスをいつ検出できますか。

正常時と不正値の挙動を確認し、上の2問を説明できれば完了です。
